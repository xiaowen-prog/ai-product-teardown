# 深度分析与评测

## 场景测试与旅程

测试卡：目标用户、原工作方式、任务目标、输入、预期交付、验收标准、环境版本、使用模式、日期、直接／间接观察、实际输出、人工修订量。

五个环节用普通话解释，并用同一任务填入具体内容：

| 环节 | 定义 | 验收关注 |
|---|---|---|
| 入口 | 用户从哪里开始这项任务 | 能否找到并进入任务 |
| 输入 | 用户交给产品的信息、材料和要求 | 条件是否齐全，缺什么 |
| 过程 | 产品怎样处理，用户在哪里参与 | AI、程序与人的分工及确认点 |
| 输出 | 产品生成了什么 | 内容、格式、版本和结果质量 |
| 交付 | 用户怎样取得并验收结果 | 真正拿到、可以使用且符合任务要求 |

**输出不等于交付：**页面有结果或写着“已生成”，不能证明用户拿到的文件合格。报告用可视化五步流程呈现，每个节点含定义、该产品的实例和验收关注点；另用短对照解释输出与交付的区别，不能只画五个抽象词。

| 阶段 | 用户做什么 | 产品给什么 | 谁拍板 | 卡点／异常 | 证据 |
|---|---|---|---|---|---|
| 入口 | | | | | |
| 输入 | | | | | |
| 过程 | | | | | |
| 输出 | | | | | |
| 交付 | | | | | |

四种异常分别记录亲测、间接观察、官方说明、未知：信息不全是否追问；失败是否说明原因及费用处理；改主意是否支持取消变更恢复；不满意能否局部修改并返回主流程。缺乏证据的分支标未测，不把入口或宣传当作实际效果。

## 自身亮点、竞品差异与比较优势

| 判断 | 在回答什么 | 需要的依据 |
|---|---|---|
| 自身亮点 | 它哪些地方做得好，值得学习 | 具体设计与观察结果，不要求独家 |
| 竞品差异 | 与明确对象相比有什么不同 | 同一任务维度、官方材料或可核实行为；未见某功能不等于对方没有 |
| 比较优势 | 在什么条件下更好、更快或更便宜 | 相应的同条件比较证据，说明任务、版本、评价标准与适用条件 |

三项分别写，不能让“尚未证明领先竞品”占满自身亮点段落。缺乏比较证据时，仍具体肯定已观察到的好设计，比较范围与限制集中交代一次。竞品也能写文书／生成文件等共同能力，不写成“只有本产品能做”。

## 用户侧交互亮点

围绕真实卡点分析，而非“简洁、智能、易用”的形容词。用“用户遇到什么困难 → 产品怎么引导 → 实际观察 → 为什么有帮助／限制”说明。选择本产品确有依据的点，不要求逐项凑齐：

| 交互切面 | 具体看什么 |
|---|---|
| 需求澄清 | 是否把含糊需求拆成用户能回答的问题，补齐遗漏约束；追问是主动还是由测试提示要求 |
| 题型设计 | 哪些用单选、多选、文本或附件；选项是否贴合用户真实表达；是否能自由补充 |
| 不确定信息 | 是否可留空、暂不确定或跳过；只看到入口不代表跳过后流程已验证 |
| 冲突与解释 | 是否发现输入矛盾、向用户解释影响、让用户决定；不能替用户虚构事实 |
| 过程反馈 | 是否显示正在处理什么、结果或错误；状态可见不等于准确或可以恢复 |
| 修改与上下文 | 用户是否无需重填条件，能修改已有结果；未改部分是否确实保留 |
| 结果接手 | 能否查看、编辑、导出或交给下一位协作者；入口与实际交付分别记录 |

观察到的设计行为标页面事实；“降低理解成本、减少提示词负担”等用户收益，若无量化证据则标合理推断。将交互问题和改进建议放在亮点之后，不用问题抹掉已观察到的亮点，也不因亮点忽略缺陷。

## 研究闭环与任务时间线

先写“本任务为什么能检验该产品的核心价值与交互设计”。对多步骤创作产品，连接素材准备、引用、生成、审阅、局部修改和最终交付，检查修改后未改部分是否保留、下游是否更新以及是否额外收费。产品不支持某一步时记录边界，不把缺失能力假设为存在。

| 时间／步骤 | 任务或节点标识 | 操作与输入 | 可见状态 | 实际结果／文件 | 费用变化 | 证据 | 对结论的影响 |
|---|---|---|---|---|---|---|---|

任务状态未知时补查已有任务和历史，避免重复计费；无新信息时不高频轮询。给出最后观察时间和缺失证据。完整任务验收与单次基础能力检查分开；局部改动须有前后证据，只有入口不算验证效果。

## 评分口径

**每份报告都要打分**，在（三）效果体验中给出总分与分段。

默认四个层级与权重（可按产品调整，合计 100%）：

| 评估维度 | 默认权重 | 核心考察点 |
|---|---|---|
| 端到端效果 | 40% | 交付物的可用性、一致性、质量 |
| 交互共创层（用户层） | 20% | 流程顺滑度、指令转化、追问与引导、改稿后能否回到主流程 |
| Agent 协作层（技术层） | 25% | 多 Agent／模块间信息传递的准确性、修改后的同步、纠偏能力、领域知识运用 |
| 基础能力层（模型与数据层） | 15% | 多模型调度的合理性、资产复用效率 |

评测表直接用满分分值表达权重：每个层级拆成 1–2 个评测维度，各维度满分加起来等于该层权重，全部满分合计 100。表头为：能力层级 / 评测维度 / 维度解读 / 打分逻辑 / 满分 / 最终得分。

- **维度解读**写这个维度考察什么；**打分逻辑**写看什么现象来给分（如“修改剧本后，后续分镜是否即时同步更新”）。
- 指标随产品类型调整：视频看一致性与音画，设计看品牌一致与文字渲染，调研看事实与来源，办公看数据正确与文件可编辑。
- **缺测的维度**：写“未测”，不计入，并把总分标为“已测维度得分（覆盖 xx/100 分）”；不能把未测当 0 分，也不能凭印象给分。
- 单次测试只代表该样本，在评级句里说明“基于 1 次测试”。
- 无法观察内部路由时，“模型调度”维度只能按结果合理性打分，并在打分逻辑中说明。

分数评级固定四段：90–100、70–89、60–69、60 以下，含义见 report.md。

## 技术分工

| 步骤 | AI／规则程序做什么 | 人做什么 | 确认方式 | 为什么需要人 | 输入输出 | 证据 |
|---|---|---|---|---|---|---|

分类依据：Chatbot 主要问答、后续由用户组织；Workflow 步骤预设，可含模型判断分支；Agent 依据目标与观察决定后续动作；多 Agent 需要多个职责主体的交接或协作证据。允许混合架构或无法确认，不凭角色标签或一次演示断言。

Agent 规格：职责、触发条件、输入、输出和验收、步骤、工具及权限、规则与能力边界、记忆／上下文读写、状态切换、交接与人工确认、失败恢复、证据和核实状态。

上下文：共享哪些字段、谁读写、角色资产如何引用、修改如何传播、版本一致性、局部回滚重跑、访问约束。数据库、RAG 或具体架构存在均需证据；只有实现需求就写可能方案。

按需提示词推导：目的、事实约束、假设、角色、输入输出、允许工具、任务规则、状态切换、确认与异常处理。明确是分析者设计方案，工具名为示意命名，不是目标真实 API；不诱导产品泄露内部提示词。

### 关键 Agent 四件套（标准报告必写）

对每个关键 Agent（或没有多 Agent 证据时的关键执行模块）依次写：

1. **逻辑梳理**：画流程图，按“输入 → 判断条件 → 分支 → 调用工具 → 推送人工确认卡片 → 写入上下文字段 → 交给下游”逐步写。分支要写清条件，例如“需求是否包含剧情、角色设定：包含则进入主流程，不包含则调用追问工具”。
2. **构成推导**：说明它更可能采用哪种架构及理由。常见对比：ReAct 适合需要不断获取外部信息、修正下一步的任务，但出错时中间 Token 多、依赖上下文窗口；Plan-and-Execute 适合长链路、高耦合的生产任务，天然支持审批流、字段级状态管理和断点续传。
3. **可用工具推导**：列工具清单，每个工具一句话写用途和触发条件。常见类别：上下文管理、状态管理、表单／确认卡片、追问、检索（RAG）、生成调用、成本估算、Agent 调度。
4. **提示词推导**：用代码块写系统提示词草案，包含角色定义、在流程中的位置、全局上下文协作协议（读哪些字段、写哪些字段）、处理流程、人工确认规则、禁止事项。标题注明“草案”。

### 全局上下文 Schema

用 YAML 代码块推导全局上下文，至少包含：项目元数据（ID、版本、规格参数）、核心内容字段、共享资产字典（角色／品牌／场景等，含资产 URI 与锁定属性）、各 Agent 的读写字段。说明它“像整个项目的 PRD”，各 Agent 靠它保持一致。

### 没做好的地方

每个问题写：现象 → 可能根因（如工具调用失败、状态更新失败）→ 提示词层改法 → 工具层改法 → 主 Agent 兜底策略（如“连续两次输出相同内容时，主控 Agent 介入检查工具和状态”）。

## 从观察行为推导技术机制

默认深度拆解按“整体协作 → 关键执行模块 → 数据与状态 → 控制与恢复”展开；达到以下解释粒度即可，不强求固定 Agent 数量或虚构后端：

- **节点与资产：**输入、结果资产、参数、引用、任务和版本如何对应；哪些是实际可见字段，哪些是分析者建议字段。
- **上下文：**每一步读取哪些已确认信息，谁修改，如何继承角色、产品或场景约束，如何防止引用漂移。
- **状态：**草稿、待确认、提交、排队、生成、成功／失败、取消等哪些可见；刷新、切会话、局部重跑会怎样。状态枚举是分析方案时明确标注。
- **局部修改：**哪些节点被更改，哪些下游需要失效或重算，哪些资产必须保留；实际行为与期望设计分开。
- **导演与人：**计划、工具调用、人工确认、权限、预算提醒／硬限额、取消和恢复如何衔接。

每个关键机制采用四列：**观察事实 → 可能实现 → 替代解释 → 验证方式**。按需给可阅读的 Schema、状态图或工具签名草案，标明“推导方案，非真实源码／接口”。数据流箭头与控制流箭头使用不同图例。找不到内部信息不等于无法分析，提出有依据且可检验的方案；也不能把方案包装成事实。

## 模型与费用

| AI 步骤 | 模态／模型／档位 | 自研或外接 | 路由依据 | 替换影响 | 用户扣费 | 成本依据／估算 | 证据与状态 |
|---|---|---|---|---|---|---|---|

成本 = 已知模型调用 + 重试 + 计算环境 + 外部接口 + 存储等，注明缺失项。Token 计费区分输入、输出、缓存；积分与货币不能默认固定等价。赠送、订阅、充值积分分别记录有效期、扣除顺序及退款规则。售价不能证明实际供应商成本或利润。

## 壁垒与判断

对每项能力问：数据或方法来源、谁能获得、为何难复制、独占或权限约束、核心任务影响、使用增长是否带来改善。复杂工作流不自动构成持久壁垒；自研能力有无优势也需证据。

结论连接场景：哪类任务、相对什么替代方案、交付质量／耗时／人工量／费用的优势与限制。改进建议连接观察问题，根因未知就保留多种解释。
