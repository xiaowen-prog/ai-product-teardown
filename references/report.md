# 报告结构、层级与交付

本文件定义**标准拆解报告**的格式，以《以 OiiOii 为例拆解一个 Multi Agent 平台》为范本。三种格式（飞书、Markdown、HTML）使用同一套结构。先完成研究，再按本结构写作；正文讲判断和机制，操作流水与证据账本放附录。

## 0. 写作风格

- **读者是产品经理。** 正文要让人读完能说出：这是什么生意、用户为什么用、它怎么做到的、哪里能借鉴。
- **标题即观点或问题。** 大章节标题点明主题，小节标题写成判断或追问，例如「垂直到只干一件事」「它每天烧这么多显卡费，靠什么回本？」「不是模型，而是工艺知识 + 编排能力」。
- **每个层级先抛问题，再回答。** 市场、商业、场景、技术各层开头列 2–4 个引导问题，例如“交互入口在哪？输入什么、输出什么？”“背后是 Workflow、单 Agent 还是 Multi Agent？”。
- **结论先行，短段落、多列表、多图。** 并列信息用列表或表格，流程和架构用图（飞书用画板，Markdown 用 Mermaid，HTML 用 SVG）。
- **证据轻量标注。** 正文不逐句挂证据编号。只在推导内容的标题或段首注明「推导」，对影响结论的未核实点用一句话说明；完整证据编号、核实状态放附录。官方声明、实测结果、分析推导三者在措辞上要分清（“官方称”“实测中”“推测”）。
- 有态度：对好的设计直接肯定并说明为什么聪明，对问题直接指出并给改法。

## 1. 标准目录

全文一个 H1。大章节用中文序号（一）到（六），作为 H2；章内小节用阿拉伯数字编号 1. / 1.1 / 1.1.1，层级依次下沉。

```text
# 以【产品】为例拆解一个【产品类型】
AI 速览 / 关键要点（编号列表）
（一）拆解产品的思路
（二）产品介绍
（三）效果体验：用一个场景测试它的能力
    1. 【场景名】
        1.1 测试维度   1.2 评估权重   1.3 能力维度评测表   1.4 分数评级
（四）产品定位：它和其他 AIGC 产品有什么差异点
    1. 【差异点一，写成判断】  2. …  3. …
（五）产品拆解：【产品】是怎么【交付核心价值】的？
    1. 市场层拆解      1.1 市场情况  1.2 竞争格局
    2. 商业层拆解      为什么能火 / 2.1 变现方式 / 2.2 护城河
    3. 场景/用户层拆解 3.1 功能模块  3.2 使用路径（正向流程 + 逆向流程）
    4. 技术层拆解      4.1 Agent 构成  4.2 逐个拆解  4.3 没做好的地方  4.4 思路从哪来
    5. 模型层拆解      5.1 模型范围  5.2 路由逻辑
    6. 基础层拆解
（六）架构总结：【产品】的架构是什么样的
附录：操作记录、证据索引、待核实清单
```

产品不适用某节时保留标题，写“不适用”及原因；信息暂缺写“待补充”，不删节。

## 2. 各章写法

### AI 速览（开头）

正文前用 5–7 条编号要点概括全文，每条以加粗短语开头，一两句写完：

1. **基础情况**：团队、阶段、用户规模或热度、面向人群、覆盖场景。
2. **差异化定位**：一句话说清相对谁、差在哪、价值是什么。
3. **测试评分**：场景名、总分、所在分段、一句话评价。
4. **核心护城河**：不是什么，而是什么。
5. **市场赛道背景**：赛道阶段与关键数字。
6. **模型调度逻辑**：用哪些模型、怎么分工。
7. （可选）**实测关键发现**：只有亲测才知道的事，如扣费规则、失败处理。

数字和判断都要能在正文里找到出处。

### （一）拆解产品的思路

用一张**方法矩阵图**说明本次怎么拆，列为：**层级 → 动作 → 产出物 → 解决的核心问题**。默认行：

| 层级 | 动作 | 产出物 | 解决的核心问题 |
|---|---|---|---|
| 商业层 | 看官网介绍 + 看创始人访谈 | 一句话定位、商业模式 | 这是一个什么样的生意／机会？如何收获第一批种子用户？ |
| 用户层 | 按场景深度体验 | 用户旅程图、完整输出物及分数 | 用户真正完成的任务是什么？它替代了以前什么工作流？ |
| 技术层 | 拆技术流程；拆背后 Agent 组成；拆解单个 Agent | 技术流程图；Agent 数量与角色；输入输出、tools、任务、规则 | 技术结构是 Workflow 还是 Agent？上下文工程起什么作用？人类分工如何映射为 Agent？哪里需要 human in the loop？如何在 System Prompt 里划清能力边界？如何防止违规、侵权？ |
| 模型层 | 分析调用的模型 | 模型列表、选择理由 | 哪些环节必须依赖强模型，哪些只是流程设计聪明？如何节省成本？ |
| 基础层 | 分析调用的数据 | 数据内容、数据来源 | 模型和流程的优势是否会随数据积累越用越强？ |

画成纵向箭头串起的分层图。随后用两三句交代观察日期、端与版本、实测范围。

### （二）产品介绍

- 一句吸引人的背景：团队、成立时间、热度（如内测排队人数），注明来源。
- 配一张产品主界面截图。
- **产品构成**：一句话说明“前台是什么 + 后台是什么”。
- **面向用户**：人群定位（如 PUGC/UGC），以及覆盖场景的子列表，每个场景一句话说明适合谁、做什么。

### （三）效果体验：用一个场景测试它的能力

- **场景标题**写清时长或规模和类型（如「30 秒人物向故事短片场景」），一句话说明选用哪个模式、测什么。
- 用代码块给出**示例 case**（输入原文）。
- **1.1 测试维度**：端到端看什么，过程能力看什么。
- **1.2 评估权重**表：评估维度 / 建议权重 / 核心考察点。默认四项为端到端效果 40%、交互共创层 20%、Agent 协作层 25%、基础能力层 15%，可按产品调整，合计 100%。
- **1.3 能力维度评测表**：能力层级 / 评测维度 / 维度解读 / 打分逻辑 / 满分 / 最终得分。每个层级 1–2 个维度，满分合计 100，给出总分。评分规则见 analysis.md。
- **1.4 分数评级**：给出分段及含义，并指出本产品落在哪段：
  1. 90–100：稳定产出高质量结果，一致性近乎完美。
  2. 70–89：流程通顺，少量人工干预即可得到不错结果，复杂细节仍有瑕疵。
  3. 60–69：存在明显的一致性或逻辑断档，但在创意启发、快速草图阶段表现好。
  4. 60 以下：高频出错，无法交付完整结果。
- 关键成品截图或成片放在本章。

### （四）产品定位：它和其他 AIGC 产品有什么差异点

- 开头一句总判断：“X 的独特点不在于模型，而在于……”。
- 列 2–4 个差异点，每个是一个 H3，标题写成判断。每点包含：创始人或官方原话（如有）、典型体现、带来的效果（对小白、对专业用户各是什么），以及与具体竞品的对照一句。
- 对聪明的设计说明为什么聪明，例如双模式“让小白一秒得到哇塞的结果，又给专业创作者留下控制感”，并说明模式之间如何串联。

### （五）产品拆解

本章开头放一张分层总览小图或引导问题。各层写法：

**1. 市场层**
- 1.1 市场情况：赛道阶段、关键数字（成本、周期、团队规模），注明来源与年份。
- 1.2 竞争格局：**分层**列出玩家，例如第一层工具／基础设施、第二层平台、第三层模型厂商。每层写代表玩家、定位、核心优势，并用一两句对比本产品与最近竞品“用户为什么买单”（为质量买单还是为效率买单）。

**2. 商业层**
- 先回答「市场上工具那么多，为什么它能火？」，用 3–4 个短语概括（产品定位、专业化 AI、交互机制、产品气质）。
- 2.1 变现方式：收费模式、价格档位、积分规则；资料不足时列出待思考的问题（订阅？按量？打包？如果你来定价会怎么定？）。
- 2.2 护城河：先说明“模型层不是护城河”及原因，再列真正的积累（工艺知识的算法化、多模型间的一致性控制、用简单界面承载复杂性），最后从产业视角总结一句。

**3. 场景/用户层**
- 开头列引导问题：交互入口是聊天框、画布还是流程连线？输入什么、输出什么？靠 Prompt 还是 UI 引导降低上手难度？
- 3.1 功能模块：按模式或入口分组（如快速／专业／创意），每组一句话说明调用了哪些 Agent。
- 3.2 使用路径：先画**正向流程**图（理想路径），再画**逆向流程**图（信息不全、生成失败、中途改主意、结果不满意时怎么走）。

**4. 技术层**
- 开头引导问题：是 Workflow、单 Agent 还是 Multi Agent？有没有接 RAG、接了哪些外部插件？如何处理不确定性（例如用户输入不全）？
- 4.1 Agent 构成：一张 Agent 构成图（主 Agent → 子 Agent → tools），一句话说明体验、流程、模型、数据各决定什么。然后按工种逐条写每个 Agent 的职责与交接关系。
- 4.2 逐个拆解：
  - **4.2.1 全局上下文**：核心问题（如何保证角色和场景一致？），说明“全局上下文像整个项目的 PRD”，并给出推导的上下文 Schema（YAML 代码块：项目元数据、核心字段、资产字典、各 Agent 读写字段）。
  - **4.2.x 每个关键 Agent**，固定四小节：
    1. 逻辑梳理：流程图 + 分步说明（输入 → 判断 → 调用工具 → 人工确认卡片 → 写入哪些字段）。
    2. 构成推导：架构选型及理由，例如 ReAct 与 Plan-and-Execute 的对比：适合什么任务、Token 成本、状态管理、审批流、断点续传。
    3. 可用工具推导：工具列表，每个工具一句话说明用途和触发条件（如“表单工具_风格选择：检索出推荐风格时推送选择卡片”）。
    4. 提示词推导：代码块给出系统提示词草案（角色定义、上下文协作协议、读写字段、处理流程、确认规则），标题注明“草案”。
  - 次要 Agent 可以只写逻辑和工具；暂时无法推导的写“待补充”。
- 4.3 没做好的地方：列观察到的问题（如工具调用失败、状态更新失败、重复确认），每条给出**提示词层**和**工具层**的改法，以及主 Agent 的兜底策略。
- 4.4 他们的思路从哪来：相关论文、竞品、用户反馈（如 MetaGPT、AgentVerse），说明对应到产品的哪个设计。

**5. 模型层**
- 5.1 模型范围：按图片、视频、文本、音频分类列出。
- 5.2 路由逻辑：一句话说明路由原则，再用表格列出：模型类别 / 模型名称 / 核心优势 / 推荐适用场景。实测或官方确认的标“已确认”，其余在表头或段首注明“推导”。

**6. 基础层**
- 3–5 条要点：一致性协议（共享 Schema）、知识库（风格库、领域知识、模型表现评分）、数据（项目数据、用户反馈）如何积累和维护，以及是否越用越强。

### （六）架构总结

**一张分层框图**收尾，固定四层，从上到下：

| 层 | 框内内容 |
|---|---|
| 用户层 | 核心功能入口（如项目创作、我的项目、资产库） |
| 应用层 | 左侧 Agent 区（主 Agent + 各子 Agent），右侧 tools 区（上下文管理、状态管理、表单、追问、RAG……） |
| 模型层 | 按图片、文本、音频、视频分组，写具体模型名，未知写“未明确” |
| 基础层 | 知识库（风格库、领域知识、模型表现评分……）+ 数据（项目数据、用户反馈） |

框内只写具体模块名，同层模块并排，不写长句。各模块之间的数据流和控制流已在技术层流程图中表达，本图不强制画箭头。

## 3. 附录

- 实测操作时间线（时间、操作、产品反馈、积分变化）。
- 证据索引：编号、来源、日期、截图路径、对应结论。
- 待核实清单：问题、当前依据、影响、验证方法、状态。
- 较长的 Schema 和提示词全文（正文放节选时）。

## 4. 格式交付

### 飞书文档
优先使用。流程图、方法矩阵、架构图用画板绘制；Schema 和提示词用代码块；表格用原生表格。用可用且有写入权限的工具创建，写入后回读核对标题层级、画板、表格，返回真实链接。无法写入时交付 Markdown 导入稿，并说明飞书文档尚未创建。

### Markdown
保存为 `.md`，图用 Mermaid（方法矩阵、流程、Agent 构成、架构总结均可），截图放相邻 `evidence/`，用相对路径，整体打包交付。

### HTML
有约定风格就遵循，否则用清晰的基础排版；图用 SVG 实际渲染；检查桌面和窄屏的可读性。不擅自公开发布。

## 5. 交付前检查

- AI 速览 5–7 条，数字和判断都能在正文找到。
- 六个大章节齐全，标题层级正确；不适用的章节写明原因。
- 拆解思路是一张方法矩阵图。
- 效果体验有示例 case、权重表、评测表、总分和分数评级。
- 产品定位有 2–4 个写成判断的差异点。
- 技术层有 Agent 构成图、全局上下文 Schema，关键 Agent 有逻辑、构成、工具、提示词四小节，并有“没做好的地方 + 改法”。
- 模型层有路由表，已确认和推导分开。
- 架构总结是一张四层框图，框内是具体模块名。
- 官方声明、实测结果、推导三者措辞分清；关键未核实点在正文提一句，完整清单在附录。
