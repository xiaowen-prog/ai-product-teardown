# 报告结构、层级与交付

三种格式共享同一结论、证据 ID 与核实状态。先完成研究与论证，再组织外发稿；不要用操作记录堆积替代产品判断。

## 1. 开头：先让读者理解产品

**【必须】正文开头用一句话交代用户需求场景、相对明确竞品的主要差异和核心价值。** 使用主文件的定位公式，紧接来源和比较范围。用户标签不能代替场景，“专业创作者”之后还要说明在什么任务、输入和约束下，需要得到什么结果。

开头同时交代产品形态、观察日期／版本和研究完成度：

- **完整场景研究：**至少一条核心交付路径已验收，局部修改和异常的验证范围明确；不代表产品全部能力已验证。
- **阶段稿：**交付仍未闭环，显著标记具体缺口、最后观察状态及影响。封面不使用让人误以为任务已成功的标题或完成率。

用少量关键判断帮助读者进入正文；每条附证据 ID 和必要限制。区分“官方主张的优势”“观察到的机制差异”“同条件实测证明的优势”。未经实测不得把前两者写成后者。

开头导读紧接一句话定位，用普通读者能理解的语言说清四件事：**具体能做什么、在行业工作里负责哪部分、哪些地方做得好、哪些工作仍交给人或尚未验证。** 配一个具体任务，写成“你给什么 → 产品帮做什么 → 拿回什么 → 谁接着处理”，不让读者从技术术语和长表里自己拼出产品职责。专业领域尤其区分材料准备、分析建议、手续辅助、最终决策与专业代理／担责；不把一个实测环节缩写成产品全部范围。

自身亮点与竞品对照各自成段：前者写已观察到的好设计及例子，后者列共同能力、可确认差异和候选差异。没有证据时写“尚不能证明相对优势”，但不要反复用这句话代替亮点评价。功能未测写“实际效果尚未确认”，不能直接写“做不到”；“不能保证／不能替代”的边界须有相应依据。关键限制集中放在适用范围处，不用每句话都加防御性说明。

## 2. 正文：结论带证据，解释因果与机制

保留七步分析的实质内容，报告大纲参考实践案例，区分**阅读章节、分析维度、架构层级**，不要把它们并排作同一级目录：

| 大章节（H2） | 章节内的小节（H3） | 范围 |
|---|---|---|
| （一）拆解思路 | 1.1 范围与证据口径；1.2 任务与验收标准 | 说明如何研究，不铺陈操作流水 |
| （二）产品介绍 | 2.1 归属与用户范围；2.2 形态与能力 | 客观介绍，官方主张有明确来源 |
| （三）效果体验 | 3.1 测试场景；3.2 输出验收；3.3 问题与边界 | 先呈现结果与关键证据 |
| （四）产品定位 | 4.1 需求与痛点；4.2 竞品差异；4.3 核心价值与限制 | 回答为什么选择它，推断有边界 |
| （五）产品拆解 | 5.1 市场；5.2 商业；5.3 场景／用户；5.4 技术；5.5 模型；5.6 基础与壁垒；5.7 五层总图 | 场景／用户含五步流程图与交互亮点，五层总图作为总结 |
| 附录 | 操作记录、二次核实、证据索引、较长推导 | 便于复核，不与正文结论混排 |

这是在案例大章节结构上展开模型、基础和总图的适配，不把新增小节冒充案例原有目录。用户另定结构时以用户为准。开头的一句话定位与关键结论可作为导读，不因此再新增一套同级大纲。

每个内容只设一个主要归属：效果章节给验收结果，技术章节解释机制；定位比较与市场背景、商业售价与模型成本相互链接，不整段重复。正文先讲结论与机制，详细流水放附录。

“场景／用户层”以可视化呈现**入口 → 输入 → 过程 → 输出 → 交付**，每步配本产品实例；单独强调输出与交付的区别。随后解释需求澄清等用户交互的具体亮点：用户卡点、交互设计、观察结果、收益与限制。开头只摘主要亮点，详细证据集中在本小节，避免全文重复。

每个主要分析单元采用：**结论 → 关键证据 → 机制／推导 → 适用范围与待核实点**。重要结论逐条编号，例如 `C012【合理推断｜待确认核实；E008、E011】`。不能只在章节末尾统一贴状态，混淆哪些主张已确认。

每一步仍汇总“已经明确确认”和“待确认核实”；影响核心判断的缺口不能全藏入附录。中间态与最终结论用不同措辞。

重要产品结论明确显示三类文字标签：**页面事实／合理推断／尚未确认**。HTML 采用稳定、不同的标签样式，并在开头给简短图例；不能只用颜色或把整个段落涂色。价格页直接展示、官方声明存在和实测文件结果可标页面事实，但官方声明不证明运行效果；可能机制与比较解释标合理推断；缺少依据或未观察到的实际结果标尚未确认。混合内容拆到句子、分句或表格单元格标记，不能用一个“页面事实”覆盖整段推导。核实进度仍单独保留，不能把“已确认”机械映射成页面事实，或把所有“待核实”都映射成尚未确认。方法定义、验收标准和建议无需硬套产品事实标签；用户举的其他产品例子不自动成为报告事实。

## 3. 附录：保留可复核的完整记录

- 完整操作时间线、任务／节点标识、测试条件及失败／恢复记录；私有标识按对外需要脱敏。
- 逐项二次验证表：问题、当前依据、影响哪些 C 编号、优先级、验证方法、实际结果、状态、还需材料。
- 证据索引：准确来源、观察与发布时间、截图、原文短摘录、视频时间戳及关联结论；避免全部指向官网首页。
- 较长的 Schema、工具与提示词推导，以及替代实现方案。正文保留理解机制必需的部分。

完整清单放附录，正文保留对读者决策重要的内容；两者互相链接而不是重复抄写。

## 4. 文字层级与重点标记

**【重点】主结论最醒目，证据次之，操作细节与附录再次之。**

- 全文一个H1报告标题；H2只用于大章节；H3用于章内小节，编号如5.4；H4用于具体机制与分析点，通常不再向下嵌套。结论C编号、事实／推断标签和证据E编号是信息标记，不是新的标题层级。不要用加粗模拟标题。
- HTML 默认不设置正文目录或顶部章节导航，除非用户要求；通过标题层级与留白组织阅读。大章节的字号、章节间距和分隔强于小节，小节强于普通正文，证据与状态标签弱于正文。不能让大章节、小节、结论卡和图题看起来同级。五层总图的五个行标签属于图内层级，不与全文大章节混排。
- 段首先给判断，随后解释原因；一段发展一个主意，长段按逻辑拆开。并列映射用表，时间与因果关系用图。
- **加粗或浅底色只标记关键词与短语**，如关键机制、决定性数字和限制；句子其他部分保持正常字重。不能用整句加粗或整段底色替代关键词标记，每个重点句通常选1—2处即可。重要性用“核心判断／关键证据／关键限制”，确定性用“事实／推断／未确认”，两个维度分开标记。
- 一个高亮块只承载一个要点；重要缺口用文字与边框提示，不只靠红绿色。未经验证的数据不能因为视觉强调而显得确定。
- 关键截图靠近论证，裁切或标注相关区域，保留原始全图供复核；清楚区分本次结果、官方示例和他人演示。
- 图表加标题、图例、说明及来源；正文引用后能直接定位。折叠区不隐藏读懂结论必须的信息。

HTML 应有稳定字号层级、段落间距和可读行宽；移动端长表可横向滚动，正文不横向溢出。风格可以之后确定，信息层级是默认要求。

## 5. 架构与流程图

五层保留用户需求场景、用户层、技术层、模型层、基础层。框内用具体模块名和简短标签，注明证据类别、状态及 ID，未知明确标记。

**【必须】五层总览是一张完整图表。** 采用同一画布上的五行矩阵或分层架构图，不以五张独立卡片、五段文字或五个章节替代。默认参考结构：左侧层级编号与名称，中间该产品的具体内容、模块与关系，右侧关键判断及证据状态；层级问题可作为小标题，不能代替产品内容。

五行分别回答：①谁在什么场景下为什么需要；②入口、输入、过程、输出、交付及已观察异常；③AI、程序、人如何分工，谁决定下一步、在哪里确认，上下文怎样传递；④具体步骤对应的模型、费用与未知路由；⑤可采购资源、特有积累及壁垒的证据。整图可沿一条代表任务纵向对齐，但不能把阅读顺序伪装成真实执行时序。

**【必须】架构图表达关系，不能只是五排功能名。** 标出相关模块之间的输入输出、引用／共享状态、模型调用、人工确认和结果回写；数据流与控制流分别给图例。若一张图太挤，采用“五层总览＋关键执行流程＋局部修改／状态图”。

五层不是固定执行顺序。需要推导的关系用虚线等明确表示，并解释推导依据；不要为画面完整虚构后台实现。

HTML 中用可实际渲染的 SVG 或结构化 HTML/CSS 绘制；五层保持同一边框、对齐关系和图题。桌面上可整体阅读；窄屏允许图表区域横向滚动或整图放大，不将正文挤出屏幕，也不把字缩到难以阅读。打印时保留五层整体，避免拆成五个不相连的块。

## 6. 格式交付

### Markdown

保存可编辑 `.md`，证据素材放相邻 `evidence/`，用相对链接便于迁移。图可用 Mermaid；目标阅读器不支持时提供 SVG 或图片。交付前检查内部引用、图片和证据 ID。

### HTML

遵循用户约定风格；未指定先用清晰基础排版。优先自包含或相邻素材，不需要后端。转义来源内容，不嵌入来源脚本，不自动公开托管。

本地HTML文件链接只能访问该文件的设备使用，不当作外发网址。用户明确要求公开网址时，使用可用发布工具，将已确认的最终报告发布到所需受众并核对部署结果，返回真实URL；之后对该公开报告的编辑同步更新原站点，保留身份与受众。没有发布授权时交付本地文件，不因“HTML”或“可外发”擅自公开；发布阻塞则说明，不编造网址。

图表实际渲染，不能只展示 Mermaid 源码。支持证据跳转与截图放大；正文关键状态直接可见。浏览器检查桌面／窄屏、链接、图片和打印布局。工具或访问受限则说明实际完成的验证，不能声称通过未做的检查。

### 飞书文档

先完成内容，再用可用且有写入权限的工具写入用户指定目标或创建新文档，不擅自扩大分享权限。回读核对标题层级、表格、截图、架构、引用和待核实清单，返回真实链接。

无法写入时先给完整 Markdown 导入稿，明确飞书创建未完成及缺少的接入条件；不能声称已创建。

## 7. 外发前验收

- 开头一句话回答谁、什么场景、什么痛点、相对谁、差异机制和核心价值；有原文依据，无无来源的人群或规模限定。
- 核心路径的结果与验收状态如实记录；未完成标阶段稿，缺口在开头醒目展示。
- 任务检验了产品关键价值与局部修改，不能仅用单次简单生成代表整个平台。
- 技术部分展开关键模块、引用、状态、上下文和控制；事实、推导、替代解释和验证方式分开。
- 结论编号与证据逐条关联，图表和正文一致；二次验证有实际结果及结论影响。
- 正文结论带证据，附录保留流水和完整待核实项；重点清楚而不过度高亮。
- 普通读者能说出产品负责哪部分工作；自身亮点、竞品差异、比较优势分清；需求澄清等交互评价有具体例子，未测能力没有写成不支持。
- 评分明细、权重与覆盖率一致；售价、扣点、最终净支出和供应商成本分开。
- 选定格式真实生成，完成范围内的显示与链接检查，研究限制如实说明。
